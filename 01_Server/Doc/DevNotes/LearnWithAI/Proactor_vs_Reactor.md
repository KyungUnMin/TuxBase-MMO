# 🌐 현대 MMO 게임 서버 아키텍처: 대칭형 vs 비대칭형 모델

이 문서는 게임 서버의 스레드 구조 설계 시 흔히 겪는 딜레마인 **역할별 전담 스레드(비대칭형)**와 **워커 풀(대칭형)** 구조의 차이, 그리고 왜 현대 서버 엔진들이 하이브리드 방식을 채택하는지에 대한 논의를 정리한 것입니다.

---

## 1. 흔한 오해: "스레드가 놀아도 CPU 코어가 일하면 되는 거 아닐까?"

초기 서버 구조를 설계할 때 흔히 다음과 같이 역할을 분리합니다.
- `Thread A` : Accept 전담
- `Thread B` : Read 전담
- `Thread C` : Write 전담

**스레드가 대기(Sleep/Block) 중일 때 OS 스케줄러가 알아서 CPU 코어에 다른 스레드를 할당한다는 사실은 정확한 OS 원리입니다.**
하지만 이 구조는 멀티코어 환경에서 **병목(Bottleneck)**과 **스케일링(Scalability)** 한계를 명확하게 드러냅니다.

### 🚫 비대칭형 분할의 한계 (병목 발생)
예를 들어 서버가 8코어 머신에서 동작 중이고, 특정 시점에 10,000명의 유저 패킷이 동시에 쏟아지는(Read 폭주) 상황을 가정해 봅시다.
- Accept와 Write 스레드는 일이 없어 대기(Block)합니다.
- Read 스레드는 미친 듯이 바쁘며 OS에 의해 1번 코어에 할당됩니다. 1번 코어는 사용률 100%를 찍습니다.
- **나머지 2~8번 코어는 현재 실행 가능한 'Read 역할' 스레드가 없기 때문에 0%로 놀게 됩니다.**
- 결국 CPU 코어는 8개나 있지만, Read 처리량의 최대 한계선(천장)은 코어 1개 수준으로 묶여버립니다.

---

## 2. 해결책: 네트워크 I/O의 대칭형 멀티프로세싱 (Symmetric Multi-Processing)

위의 병목을 해결하기 위해 최신 네트워크 I/O (Boost.Asio, epoll, IOCP) 환경에서는 **대칭형 워커 스레드 풀(Proactor 패턴)**을 사용합니다.

- N개의 모든 스레드가 똑같이 `Accept`, `Read`, `Write` 이벤트를 처리합니다 (`io_context.run()`).
- 패킷이 폭주하면 OS가 8개의 워커 스레드를 1~8번 코어에 고르게 할당합니다.
- **결과:** 8개의 코어가 동시에 패킷을 읽어 들이므로 병목 없이 처리 속도가 코어 수에 비례하여 증가합니다.

> [!TIP] 
> 현대 아키텍처에서는 성능을 위해 "특정 스레드를 기다리게 하는 블로킹 I/O" 대신, 모든 스레드가 큐를 바라보며 쉴 새 없이 비동기 작업(Async I/O)을 처리하는 것이 정석입니다.

---

## 3. 현대 MMO 서버의 '하이브리드' 아키텍처 구조

네트워크 층에서 대칭형 구조가 압도적으로 유리하다고 해서, **서버 전체가 대칭형인 것은 아닙니다.** 게임 로직까지 대칭형으로 처리하면 Data Race(충돌)와 Mutex(락) 지옥에 빠지게 됩니다. 

따라서 현대의 MMO 엔진(Unreal Dedicated, L4급 상용 엔진 등)은 **계층(Layer)별로 다른 스레딩 모델**을 채택합니다.

### 📡 3.1. Network I/O 계층 (대칭형)
- **방식:** 완벽한 대칭형 스레드 풀 (Boost.Asio `io_context.run`)
- **역할:** 패킷 파싱, 암복호화, 세션 관리.
- **특징:** 모든 워커 스레드가 차별 없이 비동기 이벤트를 퍼가서 처리. 코어를 100% 쥐어짬.

### ⚔️ 3.2. Game Logic 계층 (비대칭형 또는 분할)
- **방식:** 액터(Actor) 모델, 단일 스레드 존(Zone), 혹은 직렬화된 Job Queue.
- **역할:** 이동 판정, 전투, 스킬, 아이템 처리.
- **특징:** 여러 스레드가 동시에 같은 몬스터 HP에 접근하는 것을 막기 위해, 특정 맵(Room)이나 특정 액터의 큐(Queue)는 한 번에 하나의 스레드만 접근하도록 처리. (Lock-Free 지향)

### 🗄️ 3.3. Database I/O 계층 (전담 스레드 풀)
- **방식:** 비대칭 전담(Dedicated) DB 스레드 풀.
- **역할:** 느리고 예측 불가능한 DB 쿼리 저장 및 호출.
- **특징:** 네트워크/로직 스레드가 DB를 기다리며 멈추는 것을 방지하기 위해 백그라운드로 완전히 격리.

---

## 4. 핵심 요약 및 시사점

1. **단순 반복적이고 코어 한계까지 쥐어짜야 하는 네트워크 I/O**는 스레드별 역할을 나누지 않고 **대칭형 워커 풀 + 비동기(Async)**로 설계한다.
2. **상태 동기화와 순서가 중요한 복잡한 게임 로직**은 Data Race와 Lock 오버헤드를 피하기 위해 **분할/비대칭형(액터, 존)**으로 설계한다.
3. 이를 위해 `BoostNetEngine`은 전용 블로킹 Accept 스레드를 두는 대신, `async_accept`를 사용하여 Asio의 `io_context` 워커 풀 모델과 완벽하게 통합하는 것이 바람직하다.

---

## 5. 부록: Reactor vs Proactor 패턴 (그리고 epoll의 비밀)

네트워크 아키텍처를 이해할 때 가장 중요한 두 가지 비동기 I/O 디자인 패턴입니다.

### 🛎️ 5.1. Reactor 패턴 (epoll, select, kqueue)
- **개념**: **"준비 완료(Readiness)"**를 알림.
- **작동 방식**: OS가 스레드에게 *"지금 1번 소켓에 읽을 데이터가 도착했어!"* 라고 알려줍니다. 그러면 스레드가 직접 `recv()` 함수를 호출해서 커널의 데이터를 사용자 버퍼로 퍼와야 합니다. 
- **비유**: 식당의 **진동벨**. 진동이 울리면 손님(스레드)이 직접 카운터로 가서 음식(데이터)을 가져와야 합니다.

### 🍽️ 5.2. Proactor 패턴 (Windows IOCP, io_uring)
- **개념**: **"작업 완료(Completion)"**를 알림.
- **작동 방식**: 스레드가 OS에게 빈 버퍼를 주면서 *"여기다 데이터 꽉 채워놓고 다 채우면 알려줘"* 라고 지시합니다. OS가 백그라운드에서 데이터를 다 퍼담은 뒤, *"버퍼에 데이터 다 채워놨어! 이제 쓰기만 해!"* 라고 알려줍니다.
- **비유**: 식당의 **서빙 직원**. 손님(스레드)은 가만히 앉아있으면 직원이 테이블(버퍼)에 음식(데이터)을 다 차려놓고 알려줍니다.

> [!NOTE]
> **Q. Linux의 epoll은 Reactor인데, 왜 Boost.Asio는 Proactor 패턴인가요?**  
> Boost.Asio는 OS에 상관없이 개발자에게 무조건 Proactor 패턴(비동기 콜백 방식)을 제공하도록 설계되었습니다. Windows에서는 `IOCP`를 써서 순정 Proactor로 동작하지만, Linux에서는 `epoll`을 내부적으로 감춰두고, 데이터가 도착하면 Asio 라이브러리가 직접 `recv()`로 퍼담은 뒤에 개발자의 콜백 함수를 호출합니다. 이를 **"Reactor를 이용한 Proactor 시뮬레이션(흉내 내기)"**이라고 부릅니다. (단, 최신 커널의 `io_uring`을 쓰면 완벽한 순정 Proactor로 동작합니다.)
