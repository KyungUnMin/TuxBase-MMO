# MMORPG 프로젝트

## 프로젝트 소개

**개발 기간**: 2026.03 ~ 2026.05 (진행 중 — 이후 재개 예정)

Boost.Asio 기반 MMO 게임 서버 엔진 프로젝트입니다.   
네트워크 I/O, 자료구조, 패킷 프로토콜 등 **서버 핵심 인프라 계층의 설계와 구현**에 집중했습니다.   
이를 기반으로 동작할 게임 컨텐츠는 다음 단계에서 구현할 예정입니다.

## 기술 스택

* **언어/표준**: C++
* **네트워크**: Boost.Asio
* **테스트**: GTest
* **패키지 관리**: vcpkg
* **빌드**: CMake, Ninja
* **개발/실행 환경**: Docker (Fedora Linux 컨테이너)
  * Windows에서 소스 작성
  * Docker 컨테이너 내부에서 빌드 및 실행

## 주요 설계 및 개선 과정

### RingBuffer — 세션 수신 버퍼
TCP는 스트림 기반이기 때문에 패킷 경계가 `recv()` 호출 경계와 일치하지 않습니다.   
패킷 하나가 여러 번의 수신에 걸쳐 나뉘어 들어올 수도 있고, 한 번의 수신으로 여러 패킷이 함께 들어올 수도 있습니다.   
따라서 세션마다 아직 처리하지 않은 수신 데이터를 누적해둘 버퍼가 필요했습니다.   
이를 **read/write 커서 기반의 고정 크기 원형 버퍼(RingBuffer)** 로 구현했습니다.

#### Zero-copy 접근으로 변경
처음에는 `Read/Peek`처럼 데이터를 별도 버퍼로 복사해서 넘겨주는 방식이었습니다.   
하지만 패킷 처리 과정에서 반복적으로 발생하는 데이터 복사를 줄이기 위해, **RingBuffer 내부 메모리에 직접 접근하는 zero-copy 구조**로 변경했습니다.   
이를 위해 `RingBufferWriter/RingBufferReader`라는 RAII 핸들을 도입했습니다.   
패킷 직렬화/역직렬화 과정에서는 핸들이 제공하는 포인터를 통해 RingBuffer 메모리에 직접 데이터를 읽고 쓰도록 구성했습니다. 따라서 데이터를 별도의 임시 버퍼로 복사하지 않고 처리할 수 있습니다.   
또한 핸들이 스코프를 벗어날 때 commit이 자동으로 수행되도록 RAII로 수명과 커밋을 관리했습니다.   

#### Wrap-around 처리
Wrap-around 처리 방식도 세 번 변경했습니다.   
처음에는 **쓰기 요청이 버퍼 끝을 넘어가는 경우**, 필요한 크기만큼 **별도의 힙 메모리를 할당**해 임시 버퍼로 사용했습니다.   
이후 commit 시 임시 버퍼의 내용을 RingBuffer로 복사하고 메모리를 해제했습니다.   
하지만 wrap이 발생할 때마다 힙 할당과 해제가 발생하는 것이 부담스러웠습니다.   

그래서 별도의 할당 없이 버퍼의 앞쪽과 뒤쪽 두 영역에 대한 포인터를 그대로 제공하는 **scatter-gather 방식**으로 변경했습니다.   
이 방식은 추가 할당과 복사를 제거할 수 있었지만, 호출부에서 데이터가 두 조각으로 나뉘었는지 확인하고 각각 처리해야 한다는 사용성 문제가 있었습니다.   
결국 zero-copy라는 목표는 유지하면서 호출부의 복잡도를 줄이기 위해,  
 **남은 꼬리 공간을 건너뛰고 버퍼의 처음부터 다시 사용하는 tail-skip 방식**으로 변경했습니다.   
대신 이 방식에서는 연속된 공간이 부족할 경우 요청한 크기 전체를 한 번에 처리하지 못할 수 있습니다.   
따라서 읽기 작업은 현재 연속해서 접근할 수 있는 만큼만 반환하고, 필요한 경우 호출부가 다시 요청하도록 설계했습니다.   
각 단계에서는 특히 wrap-around와 같이 read/write 커서 계산이 꼬이기 쉬운 경계 조건을 중심으로 **GTest 시나리오**를 작성해 검증했습니다.   

#### 버퍼 소유 방식 변경
처음에는 세션마다 필요한 크기의 버퍼를 `std::unique_ptr<char[]>`로 힙에 할당했습니다.   
이후 `std::array<char, kCapacity>`로 변경해 버퍼 크기를 컴파일타임 상수로 고정했습니다.   
이를 통해 세션 생성 시 별도의 힙 할당을 제거하고, 버퍼의 소유권과 수명을 세션 객체 자체에 포함시켜 메모리 관리를 단순화했습니다.   
대신 런타임에 버퍼 크기를 유연하게 조절할 수 있는 능력을 포기하는 트레이드오프를 선택했습니다.

### 네트워크 I/O와 컨텐츠 처리 분리
네트워크 I/O와 실제 컨텐츠 처리를 분리하기 위해 **네트워크 I/O 스레드와 컨텐츠 처리 스레드를 분리하는 구조**로 설계했습니다.   
네트워크 I/O 스레드는 소켓에서 수신한 데이터를 세션의 `RingBuffer`에 쌓습니다.   
TCP 특성상 한 번의 `recv()` 호출만으로 패킷 하나가 완성된다고 보장할 수 없기 때문에, RingBuffer에 쌓인 데이터를 기준으로 패킷 헤더와 길이를 확인해 **완전한 패킷이 구성되었을 때만** 파싱을 진행합니다.   
파싱이 완료된 `Packet`은 스레드 세이프한 `LockQueue`에 넣어 컨텐츠 처리 스레드로 전달합니다.   
컨텐츠 처리 스레드는 소켓이나 RingBuffer를 직접 다루지 않고, **큐에서 전달받은 완성된 Packet만 처리**하도록 역할을 분리했습니다.   
이를 통해 각 스레드의 책임을 명확하게 나눴습니다.   

* **네트워크 I/O 스레드**
  * 소켓 I/O
  * 수신 데이터 RingBuffer 적재
  * 패킷 경계 확인
  * 패킷 파싱
  * 완성된 Packet을 LockQueue에 전달

* **컨텐츠 처리 스레드**
  * LockQueue에서 Packet 수신
  * 실제 게임 로직 처리
  * 네트워크 I/O 및 RingBuffer 직접 접근하지 않음

이 구조를 통해 네트워크 I/O와 컨텐츠 로직의 처리 책임을 분리하고, 컨텐츠 로직의 처리 시간이 네트워크 I/O 처리와 직접적으로 얽히지 않도록 구성했습니다.

## 아키텍처
```
[Client]
   ↓
[Boost.Asio]
   ↓
[Network I/O Thread]
   ↓
[Session / RingBuffer]
   ↓
[Packet Parser]
   ↓
[LockQueue]
   ↓
[Content Thread]
```
